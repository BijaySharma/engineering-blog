Say you're building a distributed cache with `N` nodes, and you need to decide which node stores a given key. The obvious approach is `hash(key) % N`: hash the key, take it modulo the number of nodes, and route the request there. This works fine until `N` changes. Add or remove a single node — which is routine in any system that autoscales or tolerates failures — and the modulus changes, which means the destination node for nearly every key changes too. In a system with a few million cached entries, one node joining or leaving can invalidate almost the entire cache at once, sending a flood of requests to your backing store right when the cluster is already in a fragile state.

Consistent hashing fixes this by decoupling "which node owns this key" from the raw count of nodes. Instead of hashing into a range `[0, N)`, you hash both keys and nodes onto the same fixed circular space — typically `[0, 2^32)`, visualized as a ring. Each node gets a position on the ring by hashing its identifier (hostname, IP, whatever is stable). To find the owner of a key, hash the key to get a point on the ring, then walk clockwise until you hit the first node. That node owns the key.

The payoff shows up when the node set changes. Removing a node only affects the keys that were mapped to it — those keys now belong to the next node clockwise, and every other key on the ring is untouched. Adding a node only steals a portion of the keys from its clockwise neighbor; nothing else on the ring moves. Instead of a near-total reshuffle, a membership change costs you roughly `1/N` of the keyspace, which is the theoretical best you could hope for.

<Callout>
In practice, a single hash-per-node produces a lumpy ring — one node can end up owning a disproportionate arc if its hash happens to land in a sparse region, especially with a small cluster. The fix is virtual nodes: hash each physical node under many labels (`node-a#0`, `node-a#1`, ... `node-a#149`) and place all of those points on the ring. More points per physical node smooths out the distribution and keeps load roughly even even when `N` is small.
</Callout>

This is also why consistent hashing shows up far outside caches: DynamoDB's partitioning, Cassandra's token ranges, and CDN request routing all lean on the same idea — pick a stable mapping from keyspace to node-space that degrades gracefully as membership changes, rather than one that treats every topology change as a full re-partition.
